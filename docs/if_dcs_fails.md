# What happens when the DCS fails

The core safety invariant in `ha.py` is: **a node may only run as primary while it holds the leader key, and the leader key can only be trusted while the DCS is answering.** Everything follows from that.

**Scenario 1: the whole DCS cluster is down (or lost quorum).** The primary's HA loop tries to update the leader key each `loop_wait` (default 10s). Writes to etcd fail or time out (`retry_timeout`, default 10s). Patroni keeps retrying, but once it can no longer guarantee renewal before the TTL (default 30s) expires, it takes the pessimistic path: it demotes itself — PostgreSQL is restarted (or stopped) into read-only operation, in `ha.py` this is the `demote('offline')` path. The reasoning is that Patroni *cannot distinguish* "DCS is down for everyone" from "I am network-partitioned and the rest of the cluster is electing a new leader right now." Since a wrong guess means split-brain, it assumes the worst. The replicas, meanwhile, cannot acquire the leader key either (no DCS = no lock), so nobody promotes. Net effect: **a healthy PostgreSQL cluster goes read-only because a completely separate etcd cluster hiccuped.** That's the trade you identified, and it's real — Patroni is explicitly CP, not AP.

**Scenario 2: only the primary is partitioned from the DCS, but the DCS itself is healthy.** Same local behavior — the primary demotes when it can't renew — but now the replicas *can* see the leader key expire, and after TTL they run the leader race and promote the best candidate. This is not a failure mode; it's the split-brain prevention mechanism working as intended. The critical timing contract is roughly `ttl >= loop_wait + 2 * retry_timeout`, which Patroni validates, so the old primary is guaranteed to have demoted (or the watchdog has fenced it) before a successor can promote.

**The failsafe mode mitigation.** Because scenario 1 annoyed a lot of operators (etcd maintenance shouldn't cause a write outage), Patroni 3.0 introduced `failsafe_mode: true` (a dynamic DCS parameter). Patroni maintains a `/failsafe` key listing all cluster members. When the primary loses the DCS, instead of demoting immediately it polls every member's REST API with `POST /failsafe`; each replica that responds is acknowledging "I still see you as leader and I'm not promoting." As long as **all** members answer, the primary keeps running writes through the DCS outage. Important caveats:

- It requires *every* member on the list to respond. One replica that is down or unreachable at the same time as the DCS outage → the primary demotes anyway. This is deliberate — an unreachable member might be on the other side of a partition where the DCS is alive and an election is happening.
- It turns the REST API into a second control channel, so its availability and security (TLS, `restapi` auth) become part of your safety story.
- It protects against DCS *unavailability*, not against Patroni bugs or a partitioned minority DCS segment feeding stale reads.

For *planned* DCS maintenance the cleaner tool is `patronictl pause`, which suspends the HA loop entirely — Patroni stops managing PostgreSQL and nothing demotes.

One more nuance worth knowing for the Kubernetes backend: there is no server-side TTL/lease like etcd's. Patroni emulates expiry by comparing timestamps written as annotations, evaluated client-side by the other members. It works, but the semantics are slightly weaker and it puts a constant read/update load on the API server — during API server degradation you get exactly the scenario-1 behavior even though kube itself "isn't down."

## Is the DCS really a SPOF?

In the hardware sense, no — you run etcd as 3 or 5 nodes with Raft, so it tolerates minority failures. In the architectural sense, yes — it's a single logical dependency whose unavailability halts writes cluster-wide (absent failsafe mode). The practical corollaries: the etcd cluster deserves the same operational care as PostgreSQL itself (dedicated disks — etcd is fsync-latency-sensitive, monitoring, backups of nothing but attention); and stretching a DCS across data centers to "solve" multi-DC HA imports etcd's quorum and latency problems into your database's control plane. Round-trip latency between Patroni and DCS eats into `retry_timeout` budgets and makes spurious demotions more likely.

## Other weaknesses of the design

**The Patroni daemon itself is a per-node SPOF — and the dangerous direction is asymmetric.** If Patroni crashes while PostgreSQL keeps running (they are separate processes; postgres survives a patroni segfault or OOM-kill), the leader key expires, a replica promotes, and the old postgres is *still accepting writes* with nobody left to demote it. This is the canonical Patroni split-brain scenario, and it's exactly what the **watchdog** exists for: Patroni pets `/dev/watchdog` and if it stops (crash, freeze), the kernel resets the machine before the TTL expires. In my experience the watchdog is the most commonly skipped piece of a Patroni deployment, which means many production clusters silently lack fencing for this case. Related: multi-second stalls of the Patroni process itself — VM freezes/live-migration, IO stalls on the config volume, a hung DNS resolution inside the single-threaded HA loop — can delay key renewal and trigger demotions or, worse, delayed demotions.

**Asynchronous replication data loss is policy, not accident.** `maximum_lag_on_failover` (default 1 MB) explicitly permits promoting a replica that is missing committed transactions. Under default settings a failover can lose up to ~1 MB of WAL plus whatever accumulates during the detection window. `synchronous_mode` closes this, but plain synchronous mode will drop back to async when no sync standby is available (availability-biased); only `synchronous_mode: strict` (or quorum commit in Patroni 4.x, `synchronous_mode: quorum`) gives a hard zero-loss guarantee, at the cost of freezing writes when standbys vanish. Consultants' rule of thumb: if the customer says "we can't lose transactions," the conversation is about sync mode and its latency, not about Patroni defaults.

**Everything rests on timing assumptions.** TTL-based leases assume bounded clock progress and bounded process pauses. NTP misbehavior, hypervisor time jumps, and long GC/GIL pauses in the Python process all erode the safety margin. The watchdog is again the backstop, with the same caveat as above.

**pg_rewind is a sharp tool.** Automatic rejoin of a former primary via `use_pg_rewind` requires `data_checksums` or `wal_log_hints`, can fail on missing WAL, and options like `remove_data_directory_on_rewind_failure` / `remove_data_directory_on_diverged_timelines` will happily delete a data directory and trigger a full re-bootstrap — correct behavior, but operationally surprising at 3 a.m. on a multi-TB cluster where re-cloning takes hours (this is where `pgBackRest`-based `create_replica_methods` earn their keep).

**REST API attack/blast surface.** The API can trigger restart, reload, failover, and reinitialize. Out of the box there's no authentication; anyone who can reach port 8008 can bounce your database. TLS + `restapi.authentication` + network policy are mandatory hardening, doubly so once failsafe mode makes the API safety-relevant.

**Configuration complexity as a failure source.** Three configuration layers (DCS dynamic config, local YAML, environment) with non-obvious precedence; `bootstrap` section applying only at cluster initialization (a perennial source of "I changed the config and nothing happened"); tag interactions (`nofailover` on the wrong node quietly reducing you to zero failover candidates); and PostgreSQL parameters that Patroni enforces versus ones it merely passes through. Misconfiguration, not code bugs, causes most Patroni incidents I've seen.

**Scope limits.** Patroni is single-cluster HA. Standby clusters give you cascading DR across regions, but promotion of a standby cluster is a manual, human-arbitrated decision — there is deliberately no automatic cross-DC failover, because Patroni has no third-site arbiter concept beyond where you place your DCS quorum. It also does nothing about logical corruption — a `DROP TABLE` or block corruption replicates faithfully to every node; HA is not backup. And logical replication clients historically lost their slot position on failover; this is only cleanly solved with PostgreSQL 17 failover slots (which Patroni 4.x supports), so on older major versions it remains a gap.

**Operational miscellany.** The HA loop is single-threaded — a slow `pg_controldata`, hung callback script, or slow DNS lookup delays everything including key renewal. Python packaging/dependency drift across OS upgrades is a real maintenance cost. On Kubernetes, the endpoint-manipulation approach can race with kube-proxy programming during rapid failovers, briefly routing traffic to the demoted pod (one reason many deployments front it with a dedicated proxy or use `pgBouncer`/service-mesh patterns).

The honest summary: Patroni's "weaknesses" are mostly *explicit design choices* — consistency over availability, TTL-based leases, delegation of fencing to the watchdog, delegation of quorum to the DCS. The failure modes are well understood and each has a documented mitigation (failsafe mode, watchdog, sync/quorum replication, backup-based replica creation). The residual risk concentrates in deployments that skip those mitigations, which is unfortunately common. If a customer needs something with different trade-offs, the alternatives shift the problem rather than remove it: shared-storage clustering (Pacemaker) moves the SPOF to storage and fencing hardware, and cloud-managed offerings move it behind an SLA you can't inspect.
